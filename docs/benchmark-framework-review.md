## Promptfoo details that matter

1. **Prompt variants:** Put prompt versions in separate files. Promptfoo evaluates each against the same test rows and providers, then displays the matrix. Change one factor at a time when comparing prompts; keep a held-out set for the final choice. [Configuration guide](https://www.promptfoo.dev/docs/configuration/guide/).
2. **Models:** Use fixed `openrouter:<model>` IDs for hosted comparisons and a separately labelled OpenAI-compatible FreeToken endpoint for local models. Promptfoo records token/cost information, and its OpenRouter provider prefers reported `usage.cost`; missing costs remain unknown. [OpenRouter provider](https://www.promptfoo.dev/docs/providers/openrouter/). The concrete model behind `openrouter/pareto-code` still needs verification in exported metadata or a wrapper; do not label its score as a fixed model.
3. **MCP distinction:** Promptfoo's [`mcp` provider](https://www.promptfoo.dev/docs/providers/mcp/) sends a JSON tool call directly to an MCP server; it tests the server, not an agent choosing tools. To evaluate agent decisions, attach a local mock MCP server to a chat model using the [MCP integration](https://www.promptfoo.dev/docs/integrations/mcp/). The docs describe executed calls in `metadata.toolCalls`, which can be graded with assertions. Verify that this path works for the chosen OpenRouter and FreeToken provider configurations; the docs explicitly show `openai:chat` and Anthropic models, not this exact combination.
4. **Coding/Pi:** A [Python custom provider](https://www.promptfoo.dev/docs/providers/python/) can call an agent and return output, token use, cost, latency, and metadata. This could wrap Pi, but only after running it in a disposable sandbox. Keep the grader separate from commands generated by the model.
5. **Fresh runs and isolation:** Promptfoo [caches model outputs by default](https://www.promptfoo.dev/docs/configuration/caching/); use `--no-cache` for repeated finalist runs. Its [beforeEach/afterEach hooks](https://www.promptfoo.dev/docs/configuration/reference/) can allocate fresh synthetic state per test, but this must be proven for any state-changing case. Use concurrency 1 initially so rows cannot share mutable fixtures.
6. **Privacy:** The [local viewer](https://www.promptfoo.dev/docs/usage/web-ui/) and [exports](https://www.promptfoo.dev/docs/configuration/outputs/) include prompts and raw outputs. Store its database, cache, exports, and traces outside Git. Promptfoo [documents telemetry and an opt-out](https://www.promptfoo.dev/docs/red-team/troubleshooting/data-handling/); disable telemetry and avoid sharing or cloud-backed graders for private HA cases. Do not pass a production MCP URL or credentials to the mock process.

## Suggested report layout

Use the built-in matrix and charts for initial inspection. In the final short decision report, show:

- A row per **task**, a column per **model × prompt version**, with pass/fail and a link to the local run detail.
- Separate totals for HA read-only, HA synthetic write, coding, and safety; never hide a safety failure inside one average.
- A small cost/latency chart per setup, with unavailable usage marked unknown rather than zero.
- Repeated-run spread for finalists, plus the exact model, provider/runtime, prompt, tool fixture, and grader versions.

The two current [smoke cases](../tasks/smoke.json) can establish that the matrix, graders, and local viewer work. They are not evidence that a model is reliable for HA or coding.
